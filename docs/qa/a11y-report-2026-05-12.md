# A11y Audit — ailevel.app — 2026-05-12

Tool: axe-core 4.10.0 injected via Claude-in-Chrome `javascript_tool`. Audit run against the live Kapitus white-label production deployment at https://ailevel.app. Each page was navigated, given ~1.5s to hydrate, then `axe.run(document, { resultTypes: ['violations'] })` was executed in the page context.

## Summary

- Pages audited: 6 of 6 (the existing browser session was already authenticated as a non-admin user, so `/learn`, `/coach`, `/assessment` and `/assessment/take` rendered real UIs; `/admin` rendered the global error boundary because the session user is not an ADMIN — recorded under "Pages with limited coverage" below).
- Pages skipped: 0. `/admin` was loaded but only the global error boundary was visible (see notes); the dev-bypass route `/api/auth/dev-bypass` returned `404` as expected for the prod build, so I did not attempt to create or invent credentials.
- Critical violations: 0
- Serious violations: 3 distinct rules across pages (`aria-prohibited-attr` on `/learn` & `/coach`; `link-in-text-block` on `/sign-in`; `aria-progressbar-name` on `/assessment/take`)
- Moderate violations: 3 distinct rules (`heading-order` on `/sign-in`; `page-has-heading-one` on `/assessment/take`; `landmark-one-main` + `region` on the `/admin` error-boundary page)
- Pages with no in-app violations: `/` (only an extension-injected element flagged), `/assessment`

### Notes on what was filtered out

axe also flagged two items injected by browser extensions / devtools overlays. They are **not in our codebase** and should be ignored when triaging:

- `nested-interactive` on `<div class="acrobat-button" role="button" aria-label="Get summaries and key insights using AI Assistant">` — Adobe Acrobat browser extension overlay on `/`.
- `region` on `#claude-static-indicator-container > span` — the Claude-in-Chrome extension's own status indicator.

The findings below exclude those two.

## Per-page findings

### `/` (marketing landing — "From zero to AI hero")

No in-app axe violations after filtering out the Acrobat-extension overlay.

### `/sign-in`

- **[serious] link-in-text-block** | `body > .min-h-screen.flex-col.flex > main > .lg\:py-24.bg-kp-mist.py-16 > .max-w-md.mx-auto.sm\:px-8 > .mt-6.text-center.text-kp-ink-mute > a[href="mailto:hello@ailevel.app"]` | `<a href="mailto:hello@ailevel.app" class="text-kp-purple underline-offset-2 hover:underline">Contact support</a>` — link only differentiated by colour (`#ad00ff` on `#64748b`, contrast 1.04:1) with no persistent underline; fails 1.4.1 Use of Color and the link-in-text-block contrast minimum (3:1).
- **[moderate] heading-order** | `body > .min-h-screen.flex-col.flex > footer > .lg\:py-20.max-w-kp-container.py-16 > .grid.grid-cols-2.gap-10 > div:nth-child(2) > h3` | `<h3 class="kp-eyebrow text-kp-ink">Academy</h3>` — footer column header skips from the page's `h1` straight to `h3`. Either demote to `<p>`/`<div>` styled as an eyebrow or use `<h2>`.

### `/admin` (admin dashboard)

The current browser session is not an ADMIN, so the route rendered the global error boundary (`SYSTEM EXCEPTION — Something disconnected.`) rather than the real dashboard. Findings below are for **the error page only** — the real admin UI was not auditable without an admin account.

- **[moderate] landmark-one-main** | `html` | error page has no `<main>` landmark.
- **[moderate] region** | `.text-danger` ("SYSTEM EXCEPTION" eyebrow), `.space-y-2` (heading + paragraph block), action-button container | content sits outside any landmark.

Action for triage: re-audit `/admin` once an admin test account exists (or once the dev-bypass is enabled in a non-prod environment). The findings above probably also apply to other error/empty states across the app since they share the same global error component — worth a single fix.

### `/learn` (employee home)

- **[serious] aria-prohibited-attr** | `.sm\:hidden > .gap-0\.5[aria-label="0-day streak"]` | `<span class="flex items-center gap-0.5" aria-label="0-day streak">` — `aria-label` on a `<span>` with no `role`. Either give the span `role="img"` (it appears to be a flame/streak indicator), wrap the value in a `<p>` with a `.sr-only` label, or move the `aria-label` to a focusable/role-bearing parent.

### `/coach` (AI coach chat)

- **[serious] aria-prohibited-attr** | `.sm\:hidden > .gap-0\.5[aria-label="0-day streak"]` | `<span class="flex items-center gap-0.5" aria-label="0-day streak">` — same shared header/streak component as `/learn`; one fix covers both.

### `/assessment` (baseline assessment intro)

No axe violations.

### `/assessment/take` (assessment runner — audited as bonus since the session allowed it)

- **[serious] aria-progressbar-name** | `.transition-\[width\]` | the assessment progress bar has `role="progressbar"` (implicit or explicit) but no `aria-label`, `aria-labelledby`, or `title`. Add `aria-label="Assessment progress"` (and ideally `aria-valuenow` / `aria-valuemin` / `aria-valuemax`) to the progress element.
- **[moderate] page-has-heading-one** | `html` | the take page has no `<h1>`. Add an `<h1>` for the current question section or for the assessment title (it can be visually hidden with `.sr-only` if the design doesn't want a big heading).

## Recommendations for the triage pass

1. The "0-day streak" `aria-prohibited-attr` finding lives in a shared header component (visible on `/learn` and `/coach`, presumably any authenticated shell). One fix in the streak badge component clears two pages.
2. `link-in-text-block` on `/sign-in` is a brand-token issue — the `text-kp-purple` on `text-kp-ink-mute` combination is below the 3:1 link-contrast threshold. Either always-underline support links in muted paragraphs, or pick a brand purple with sufficient contrast against the muted slate.
3. The error boundary's missing `<main>` landmark is a likely repeat across every error/empty state — fix the shared `Error`/`NotFound` component.
4. The `<h3 class="kp-eyebrow">Academy</h3>` in the footer is a global pattern — likely impacts every page with the footer; the audit only flagged it where the page tree exposed it.
5. `/admin` needs to be re-audited with a real admin session before the a11y task can be considered fully closed. The error-boundary findings are not a substitute.
